# 群排行（暂定名）

## 微信群专属排行榜与用户共创模板平台

**产品方案 PRD v0.1**

版本日期：2026-10-26\
项目类型：微信小程序\
初期主体：个人开发者（待验证审核可行性）\
产品阶段：需求分析与技术预研

---

# 一、项目背景

## 1.1 项目起源

项目最初源于微信群内关于痛风和尿酸的讨论。

群友希望通过一个简单的工具，分别填写自己的尿酸检测结果，并自动生成群内排行榜，供群友查看、比较和互动。

进一步讨论后发现，这不是一个只服务尿酸场景的需求。

微信群中存在大量类似的排行需求：

- 尿酸数值排行
- 卧推重量排行
- 游戏战绩排行
- 跑步成绩排行
- 熬夜时间排行
- 每月打卡排行
- 群友自创趣味排行

这些玩法的共同特点是：

1. 参与者属于某个微信群。
2. 需要填写一定结构的数据。
3. 根据指定规则形成排名。
4. 成绩需要能够持续更新。
5. 希望在微信群中传播和互动。

因此，决定将产品发展为通用群排行平台。

## 1.2 最终产品定位

**一个面向所有微信用户、以微信群为独立空间、允许用户自定义排行规则，并通过公共模板库传播玩法的小程序。**

产品核心理念：

**万物皆可排，群友自己定。**

产品不是传统社交平台，也不是问卷工具，而是以排行榜为核心的轻量级用户共创平台。

# 二、核心产品原则

## 2.1 人人可以使用

任何符合平台准入条件的微信用户都可以：

- 创建排行榜玩法
- 使用官方模板
- 加入群排行
- 提交和维护自己的成绩
- 创作自定义场景
- 将自己的玩法投稿到模板库

不需要平台管理员为每一个群创建排行榜。

## 2.2 群是数据隔离单位

每个微信群拥有独立的排行空间。

同一个微信群允许存在多个排行榜。

不同微信群即使使用同一个模板，也不共享成绩、成员和统计结果。

一个用户可以同时参与多个群空间。

## 2.3 模板可以公开，成绩默认私有

模板描述玩法规则，不包含实际参与者的数据。

公共模板库允许跨群浏览和使用。

群内真实成绩默认只对获准成员开放。

## 2.4 用户定义玩法，平台限定能力

允许用户自定义主题、字段、单位和排名规则。

但用户只能从平台支持的字段类型与安全计算规则中选择。

不允许用户提交任意可执行代码或脚本。

## 2.5 低使用门槛

主要使用流程应尽可能简单：

选择模板或自行创建 → 分享到微信群 → 群友填写 → 自动排行。

首版不开发独立聊天、论坛和评论系统。

# 三、产品核心模型

整个系统区分以下五个概念。

## 3.1 场景（Scenario）

场景是一种排行榜玩法的业务概念。

例如：

- 尿酸巅峰赛
- 群友卧推挑战
- 魔兽副本竞速
- 每月跑步里程挑战

场景本身不直接存储成绩。

## 3.2 模板（Template）

模板是场景的结构化定义。

包含：

- 标题
- 描述
- 分类
- 字段 Schema
- 录入校验规则
- 排名规则
- 统计周期
- 默认展示配置
- 隐私风险分类

模板存在两种来源：

**官方模板**：平台维护的标准玩法。

**用户模板**：用户创建并经平台审核后发布到公共模板库的玩法。

## 3.3 群空间（Group Space）

群空间代表一个微信群对应的独立业务空间。

包含：

- 群空间 ID
- 群标识映射
- 成员及角色
- 群内排行榜
- 空间管理配置

群空间不应依赖读取真实微信群成员列表。

微信群身份识别及群成员权限验证属于必须单独验证的微信平台能力。

## 3.4 榜单实例（Leaderboard）

榜单实例是模板在某个群内的实际使用结果。

例如：

官方尿酸模板 → A 群尿酸排行榜。

同一个模板可以创建多个相互独立的榜单实例。

群内榜单可以在允许范围内调整显示名称、开放周期等配置。

## 3.5 成绩记录（Entry）

记录用户实际提交的数据。

例如：

- 尿酸：568 μmol/L
- 测量日期：2026-10-26
- 测量方式：医院化验
- 备注：周末聚餐后测量

一名用户可以拥有多条历史成绩记录。

排行榜根据预设规则从记录中计算当前名次。

# 四、主要用户角色

| 角色     | 主要权限              |
| ------ | ----------------- |
| 普通用户   | 参与排行、维护自己的成绩      |
| 玩法创作者  | 创建、编辑个人玩法、投稿模板    |
| 群空间管理员 | 管理群空间、榜单和成员       |
| 榜单创建者  | 维护自己创建的榜单         |
| 平台审核员  | 审核投稿、处理举报、下架违规模板  |
| 平台管理员  | 管理官方模板、类目、规则和系统配置 |

角色与权限分离。

模板作者不能自动获取使用该模板的各个群的成绩数据。

# 五、核心业务功能

## 5.1 首页

建议包含：

- 我的群排行
- 创建排行榜
- 模板库入口
- 我创建的玩法
- 最近参与的排行榜

首屏优先展示用户已经参与的群和榜单。

## 5.2 群空间

一个群空间包含：

- 群空间首页
- 本群排行榜列表
- 创建排行榜
- 成员管理
- 空间设置

群成员可以在适当权限下自由创建新榜单。

初期可以允许任何已授权成员创建榜单，管理员拥有管理和关闭权限。

## 5.3 榜单详情

展示：

- 榜单名称
- 玩法说明
- 当前排名
- 排名成绩
- 辅助信息
- 我的排名
- 提交或更新成绩
- 历史记录
- 排序和统计周期说明
- 分享入口

用户点击某位参与者时，只能查看对方授权公开的榜单信息。

## 5.4 成绩录入

系统根据模板的字段 Schema 动态生成表单。

表单支持：

- 必填校验
- 类型校验
- 数值范围校验
- 单位显示
- 自定义选项
- 默认值
- 字段说明
- 数据编辑与删除

系统自动记录提交者和提交时间。

## 5.5 榜单管理

支持：

- 修改非破坏性展示设置
- 暂停提交
- 关闭榜单
- 删除榜单
- 删除违规记录
- 管理参与者
- 查看审核与操作日志

修改字段结构或排名算法应采用版本化方式，避免破坏已有数据。

# 六、自定义字段系统

## 6.1 字段类型

首版推荐支持以下类型。

| 字段类型 | 示例       | MVP     |
| ---- | -------- | ------- |
| 整数   | 引体向上次数   | 支持      |
| 小数   | 尿酸、重量、距离 | 支持      |
| 时长   | 跑步用时     | 支持      |
| 日期   | 测量日期     | 支持      |
| 时间   | 睡觉时间     | 支持      |
| 单选   | 游戏难度     | 支持      |
| 多选   | 标签集合     | 支持      |
| 短文本  | 备注       | 支持，内容审核 |
| 布尔值  | 是否完成     | 支持      |
| 图片   | 比赛凭证     | 后续版本    |
| 文件   | 化验报告     | 暂不支持    |
| 地理位置 | 运动地点     | 暂不支持    |

健康类模板可以根据合规要求限制或禁用自由文本及图片等字段。

## 6.2 字段属性

每个字段支持配置：

- 字段唯一标识
- 展示名称
- 字段类型
- 是否必填
- 默认值
- 提示文案
- 单位
- 最小值
- 最大值
- 最大文本长度
- 单选或多选选项
- 是否参与排名
- 是否在榜单上展示
- 信息敏感级别

## 6.3 字段数量

首版建议：

- 1 个主要排行指标
- 最多 5 个辅助字段
- 最多 1 个短文本备注字段

这些是建议的产品限制，可以配置调整。

## 6.4 用户动态建模方式

普通用户不直接编辑 JSON Schema。

小程序通过可视化表单配置字段。

例如：

创建「卧推力量榜」

1. 添加主要字段：卧推重量，数字，单位 kg。
2. 添加辅助字段：次数，整数。
3. 添加辅助字段：是否使用辅助，单选。
4. 添加辅助字段：测试日期，日期。
5. 选择排名规则：历史最高重量。

系统自动生成录入页面和排行页面。

# 七、排名计算引擎

## 7.1 核心设计

**表单数据和排名算法必须分离。**

一条提交记录包含所有字段，但只有被排名规则指定的字段参与计算。

## 7.2 首版计算方式

| 规则      | 含义      |
| ------- | ------- |
| Latest  | 最新有效成绩  |
| Max     | 历史最高成绩  |
| Min     | 历史最低成绩  |
| Sum     | 有效记录累计  |
| Count   | 有效记录次数  |
| Average | 有效记录平均值 |

支持升序、降序。

## 7.3 统计周期

支持：

- 全部时间
- 本周
- 本月
- 自定义日期区间

需要明确周期根据记录的测量时间还是提交时间统计。

不同场景可能存在不同要求。

## 7.4 并列排名

首版建议使用标准竞赛排名：

第一、第二、第二、第四。

当主要指标相同时，默认同名次。

未来支持次级排序字段，例如卧推重量相同，再比较完成次数。

## 7.5 复合计算

中期支持受控表达式：

- A + B
- A - B
- A × B
- A ÷ B
- 加权求和
- 固定条件计分

例子：

卧推总训练量 = 重量 × 次数。

跑步平均配速 = 时长 ÷ 距离。

实现时不运行用户提交的 JavaScript。

采用受控 AST、字段类型校验及预设运算符，并限制表达式复杂度和计算成本。

## 7.6 用户记录模型

默认允许多次提交，保留成绩历史。

排行榜引擎根据规则生成一个当前成绩。

这样可以同时支持最新尿酸值、卧推最高纪录和每月累计里程。

# 八、公共模板库

## 8.1 模板库定位

模板库不是成绩广场，而是**排行榜玩法市场**。

所有用户均可以浏览已经公开上架的模板。

## 8.2 模板分类

初期可以提供：

- 运动健身
- 游戏竞技
- 日常生活
- 学习成长
- 趣味整活
- 健康记录（受限场景）

其中健康类模板不默认具备所有普通模板的权限。

## 8.3 模板内容

模板详情展示：

- 模板名称
- 玩法简介
- 作者名称
- 字段列表
- 排名规则
- 录入示例
- 榜单效果预览
- 使用次数
- 最近更新日期
- 使用模板创建群排行

公开的示例数据必须使用虚构数据，不能复制原群真实用户成绩。

## 8.4 模板创作流程

用户从空白配置或官方模板开始创作。

流程：

1. 定义主题。
2. 配置字段。
3. 选择排行规则。
4. 预览表单和结果。
5. 保存为个人玩法。
6. 在群内创建榜单。
7. 可选：申请投稿公共模板库。

用户可以在群内使用自己尚未公开上架的玩法，但依然必须经过平台必要的即时内容安全校验。

## 8.5 公开投稿审核

投稿后进入审核队列。

状态包括：

- Draft：草稿
- Pending：待审核
- Approved：审核通过
- Rejected：审核拒绝
- Published：已上架
- Removed：已下架

审核要点：

- 主题是否违法违规
- 名称和描述是否合规
- 字段及选项是否含违规内容
- 是否涉及敏感个人信息
- 是否可能鼓励危险行为
- 是否涉及医疗建议或其他需要资质的服务
- 排名规则是否有效
- 是否存在仿冒或垃圾投稿

审核通过的模板才能在公共模板库中供所有用户浏览。

## 8.6 模板版本

每次公开发布形成一个不可变版本。

群内实例绑定具体版本。

模板作者更新规则后，已经创建的群榜单不自动改变。

管理员可在兼容性校验后主动升级。

模板被作者撤回时，不应无条件删除其他群的数据；涉及违法违规内容则可以由平台强制停止使用相应玩法。

# 九、微信群空间与身份识别

这是整个项目的技术高风险部分。

## 9.1 理想体验

用户在微信群中打开小程序。

系统识别来源群，进入其对应的群排行空间。

不同群进入不同空间。

同一个群内的所有排行榜集中管理。

## 9.2 微信能力边界

`openGId` 可作为群标识方案的研究方向，但必须确认目标是普通微信小程序而非小游戏，以及当前基础库、入口场景、API 可用性和权限条件。

不能假设：

- 可以获取微信群全部成员。
- 可以读取群昵称、群公告等任意信息。
- 可以实时知道某人是否退出微信群。
- 可以在任何入口稳定获取群 ID。
- 获取群 ID 就意味着用户已经通过成员身份验证。

因此微信群自动识别必须先进行独立技术验证。

## 9.3 推荐群空间绑定方案

采取渐进式设计：

**优先方案：微信群标识绑定**

在微信支持的场景中获取经过验证的群标识，映射到平台内部 Group Space。

**降级方案：邀请式群空间**

由用户创建内部群空间，分享邀请卡片，其他用户主动申请加入。

此时语义是“群成员共同使用的私有空间”，不是严格证明真实微信群成员身份。

## 9.4 数据隔离原则

所有涉及群数据的服务端操作必须验证：

- 当前登录用户
- 所属群空间
- 用户在群空间中的权限
- 榜单是否属于此空间
- 成绩是否允许访问

不能单纯通过隐藏前端页面实现隔离。

## 9.5 跨群转发

A 群的榜单卡片被转发到 B 群时：

- 不自动公开 A 群成绩。
- 未授权用户无法访问 A 群成员数据。
- 不自动将 B 群用户加入 A 群。
- 可以提供“用同一模板创建本群新榜单”的操作。

该设计兼顾隐私和模板传播。

## 9.6 成员离群

普通小程序无法保证实时获知群成员变化。

需要接受技术边界，并通过成员审批、访问失效、重新验证及管理员移除机制降低风险。

不得对用户承诺技术上无法保证的绝对群成员隔离。

# 十、隐私和内容安全

## 10.1 数据分类

建议按风险划分：

**普通记录数据**

例如游戏分数、打卡次数。

**可能涉及个人隐私的数据**

例如收入、消费、位置。

**敏感个人信息**

例如能够关联到个人的医疗健康数据。

不同分类适用不同权限和信息处理策略。

## 10.2 健康类场景

尿酸排行榜涉及个人健康数据。

必须明确：

- 收集目的
- 数据展示范围
- 记录是否公开
- 信息保留期限
- 删除方式
- 撤回同意方式

涉及敏感个人信息时应履行适用的单独同意要求。

不提供医疗诊断、用药推荐和治疗方案。

也不应该通过成就系统鼓励用户追求异常危险的健康数值。

## 10.3 排行隐私设置

建议平台具有不可被用户绕过的隐私底线。

对于普通榜单：

- 群空间授权成员可见
- 用户可以删除自己的记录

对于敏感榜单：

- 单独告知和授权
- 限制字段与可见范围
- 不允许将真实成绩投稿模板库
- 必要时限制显示具体数值
- 支持立即撤回与删除

## 10.4 UGC 内容审核

内容审核至少覆盖：

- 用户自定义榜单标题
- 场景描述
- 字段名称
- 单选和多选选项
- 备注内容
- 模板投稿内容
- 后续图片内容

建议实现：

- 服务端文本检测
- 风险命中拦截
- 举报入口
- 管理员删除
- 违规用户限制
- 审核记录
- 公共模板人工复核

**群内使用不等于免审核。**

## 10.5 个人主体发布

现阶段不能认定个人主体一定能够通过审核。

需要验证：

1. 个人主体实际开放的服务类目。
2. 通用排行工具属于哪个类目。
3. 用户自定义主题是否触发额外审核要求。
4. 公共模板投稿是否属于更严格的内容平台场景。
5. 健康类记录功能是否触发特殊资质要求。
6. 所选技术能力是否对主体类型有限制。

产品设计应支持根据审核结果逐步启用功能。

# 十二、技术架构

## 12.1 推荐技术选型

**小程序前端**

- uni-app + Vue 3
- TypeScript
- Pinia
- 微信小程序运行端

建议使用 Vue 3 而不是继续沿用 Vue 2，以便后续维护。

**后端**

初期有两种选择：

方案 A：微信云开发 / CloudBase。

优点是接入微信生态简单、减少独立基础设施管理。

方案 B：Node.js + PostgreSQL + Redis。

优点是更适合复杂查询、版本化 Schema、审核后台及未来扩展。

**倾向方案：**

如果优先快速验证微信能力与审核，使用云开发。

如果从一开始就要建设完整的模板和规则平台，可以采用 Node.js + PostgreSQL，同时利用微信登录和相关开放能力。

## 12.2 建议分层

- Identity：用户身份
- Group：群空间及成员权限
- Template：模板与字段 Schema
- Entry：成绩采集与校验
- Ranking：排名计算
- Moderation：内容审核
- Privacy：隐私授权
- Admin：平台管理

应避免把群隔离、排名规则和模板配置耦合到同一个业务模块。

## 12.3 排名计算策略

初期优先实时数据库查询或服务端聚合。

针对更新频率较高的榜单，引入缓存。

对累计型榜单增加增量计算或按需重新计算机制。

所有计算由服务端完成。

## 12.4 后台管理

建立独立 Web 管理后台。

最小功能包括：

- 模板投稿审核
- 官方模板管理
- 分类管理
- 风险内容处理
- 用户与榜单封禁
- 系统参数设置
- 基础运营统计

不建议在小程序内开发完整的平台管理系统。

# 十四、迭代规划

## P0：技术与审核可行性验证

**目标：确认关键微信能力是否可行。**

任务：

- 注册或检查个人主体小程序
- 核对服务类目
- 验证群来源识别
- 验证分享卡片行为
- 验证 OpenID 身份体系
- 验证隐私接口调用
- 验证 UGC 内容安全流程
- 完成最小版本提审

验收标准：

能够明确区分哪些能力可用、有限可用或不可用。

不把未验证的群身份识别作为正式架构的强依赖。

## P1：基础排行榜 MVP

功能：

- 微信用户身份
- 群空间
- 创建排行榜
- 单主指标
- 辅助字段
- 提交成绩
- 排名展示
- 分享邀请
- 成绩编辑与删除
- 基础内容审核和隐私控制

暂不开放公开用户模板投稿。

## P2：自定义玩法引擎

功能：

- 动态字段配置
- 多种字段类型
- 排名聚合模式
- 统计周期
- 表单实时预览
- 草稿保存
- 模板版本管理

目标：

让普通用户不写代码即可创建新玩法。

## P3：公共模板库

功能：

- 官方模板分类
- 用户投稿
- 审核后台
- 上架与下架
- 模板版本
- 模板使用统计
- 一键创建群榜单

目标：

形成用户创作、平台审核、群内传播的完整闭环。

## P4：高级玩法

可能包含：

- 复合计算公式
- 多指标排序
- 榜单赛季
- 历史趋势
- 分享海报
- 排名变化提醒
- 成绩凭证
- 投票型排行
- 模板作者主页

这些功能均应基于真实用户反馈决定优先级。

# 十五、非目标

至少在首版明确不做：

- 全站公开个人成绩排行

这些边界有助于控制研发复杂度和审核风险。

# 十六、关键风险

| 风险        | 影响        | 处理策略            |
| --------- | --------- | --------------- |
| 个人主体类目不支持 | 无法按原计划上线  | 先提审验证，必要时调整主体   |
| 群标识能力受限   | 无法精准关联微信群 | 采用独立群空间邀请机制     |
| 无法实时验证群成员 | 成员权限可能不同步 | 审批、重新验证和管理员移除   |
| 用户提交违规内容  | 内容安全风险    | 自动审核、举报、人工治理    |
| 敏感健康数据泄露  | 隐私及法律风险   | 数据最小化、单独同意、权限隔离 |
| 用户规则过于复杂  | 计算逻辑不可控   | 受控规则引擎          |
| 模板升级破坏数据  | 排行结果错误    | 固定版本和迁移机制       |
| 榜单恶意刷成绩   | 排名可信度下降   | 提交频控、异常检测、管理员处理 |

# 十七、成功指标

MVP 阶段重点观察：

- 创建榜单的用户比例
- 榜单创建完成率
- 每个榜单的参与人数
- 分享后加入转化率
- 每个用户的成绩更新次数
- 7 日及 30 日群榜单活跃率
- 用户自定义玩法占比
- 模板复用次数
- 内容审核拦截率
- 隐私撤回及删除请求处理情况

后期重点观察：

**一个用户创建的玩法，是否能够在其他群中自然传播并被重复使用。**

这将是产品是否形成真正模板生态的重要指标。

# 十八、当前决策与待验证事项

## 已明确的需求

1. 产品面向所有符合条件的微信用户。
2. 以微信群为核心使用场景。
3. 每个群拥有独立排行榜数据。
4. 一个群可以拥有多个榜单。
5. 用户可以自行定义排行场景。
6. 排行不局限于单一数字。
7. 需要支持可配置字段和计算规则。
8. 平台提供少量官方模板。
9. 用户可以申请投稿自己创建的模板。
10. 公开模板必须经过平台审核。
11. 模板可跨群复用，但成绩不可跨群泄露。

## 推荐但尚未最终确定

1. 首版一个主排名字段加最多五个辅助字段。
2. 先提供预设聚合规则，不开放任意复杂公式。
3. 默认保留成绩历史。
4. 群空间采用管理员与成员角色模型。
5. 公共模板库与群内榜单采用不同内容治理流程。
6. 不开放用户评论、聊天和图片上传。
7. 首版优先验证一个完整的群内闭环。

## 需要技术或平台验证

1. 普通微信小程序实际可用的群识别机制。
2. 个人主体的类目与 UGC 准入限制。
3. 公开用户模板库能否按当前主体和功能审核通过。
4. 隐私接口与敏感数据处理要求。
5. 不同入口下的群身份验证一致性。
6. 关键第三方服务和基础设施费用。
7. 业务主体升级时的数据及小程序迁移路径。

# 十九、产品最终愿景

让微信群里的任何一个人，都能用几分钟创建一个属于自己群的排行榜。

玩法由用户定义，数据由群友填写，名次由系统计算。

优秀的玩法经过平台审核进入公共模板库，被其他微信群发现、使用和二次创作。

**最终形成一个“用户创造排行玩法、微信群消费玩法、平台分发玩法”的轻量级生态。**

产品最大的壁垒不应该是排行榜计算本身，而应是：

- 足够好用的玩法编辑器
- 丰富的用户原创场景
- 可靠的群空间隔离
- 安全且稳定的规则引擎
- 高质量的公共模板库

**一句话总结：群排行是一个以微信群为私有数据空间、以动态字段和排名规则为基础、以用户共创模板为增长核心的排行榜平台。**
